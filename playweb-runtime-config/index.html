Infrastructure

PlayWeb Runtime Configuration

The settings that tell PLAY where its backend services live — along with sign-in details, an encryption key, and per-organization preferences — are now handed to the application automatically each time it loads, instead of being permanently fixed in place ahead of time. A deployment can now be repointed or adjusted with a configuration change alone.

01

What changed

From "fixed in place" to "supplied on load."

Previously, the addresses of the services PLAY depends on, along with its identifying code and a couple of secrets, were permanently fixed at the time the application was prepared. Changing any of them meant updating every deployed copy individually, or preparing the application all over again. Those same settings are now supplied automatically the moment the application loads, from a single, central configuration.

One place to change it

An administrator managing a deployment now only ever needs to touch that central configuration — never the application itself — to update any of these values.

02

Configuration is now served on demand

The application asks for its settings every time it loads.

Right before PLAY shows anything on screen, it asks for its current configuration. That configuration is assembled from local settings and, where a value isn't set locally, from each organization's own central configuration. If a value is missing everywhere, the application is told so plainly rather than being left to guess at a value that might be wrong.

A restart is still needed after a change

The underlying service only reads its configuration once, when it starts. Refreshing the page alone isn't enough — the service has to be restarted first so it picks up the new values.

03

A working development/production switch

A setting that now actually takes effect, replacing one that quietly never did.

PLAY has always needed to behave slightly differently depending on whether it's running on a developer's own machine or in a real deployment — for example, whether it should trust a configured address exactly as written, or work out the right address on its own. That decision used to rely on a setting that was permanently locked in place ahead of time and could never actually change afterward, no matter what a deployment's configuration said — so in practice it stopped reflecting reality soon after.

That decision is now driven by a single, plain switch that's read fresh every time the page loads. Flipping it from one value to the other takes effect on the very next page refresh.

Development mode for a developer's own machine

Configured addresses are trusted exactly as written, even if they point somewhere entirely different from where the application itself is running.

Production mode the safe default for real deployments

Only the meaningful part of a configured address is kept; the rest is always completed automatically. A leftover address from someone's local setup can no longer accidentally leak into a live deployment.

04

Nucleus keeps its own address

The one service that's allowed to live somewhere else entirely.

Every other service PLAY talks to is assumed to sit alongside PLAY itself. Nucleus is the one exception — it commonly runs on a completely separate machine — so its address is always trusted exactly as configured, in every environment, rather than ever being worked out automatically.

05

Secrets are no longer fixed in place

Two values that used to be locked in ahead of time are now supplied on load instead.

Encryption key protects data saved in the browser

The key PLAY uses to encrypt information it stores locally is now supplied automatically at load time, sourced from central configuration, instead of being permanently fixed in place ahead of time.

AI assistant display name shown in the AI chat panel

The name shown for the AI assistant is now taken from each organization's own preferences, so different organizations can each see their own preferred name, instead of every deployment being stuck with one fixed name.

06

Safer handling of configuration values

The values that can carry real credentials are treated with more care.

Kept out of shared storage stays local to each deployment

Configuration that can carry real credentials is no longer stored anywhere shared. A sanitized example with placeholder values is provided instead, so anyone setting up a new deployment starts from a safe template rather than a copy carrying someone else's real secrets.

Checked at startup missing values are reported, not guessed

When the underlying service starts, it checks that every setting PLAY truly needs is available from somewhere. Anything still missing is reported clearly at startup, instead of silently showing up as a broken behavior later on.

Kept out of prepared copies only the safe template is ever included

Preparing a new, distributable copy of PLAY now only ever includes the sanitized placeholder template, never real credentials. A real configuration still has to be put in place for each deployment separately.

07

Organization-level settings

Preferences and connection details each organization can set for itself.

In addition to the deployment-wide settings above, PLAY supports a broader set of settings that each organization using it can configure independently. These control everything from how that organization's data is stored, to which optional features and display options are turned on for its users.

08

Good to know

A few things that come up when working with this configuration.

I changed a setting but the application still shows the old one. Why?

The underlying service only reads configuration once, at startup — it needs to be restarted, then the page refreshed. A refresh alone isn't enough if the service itself hasn't picked up the change yet.

Why does Nucleus behave differently from the other services?

Nucleus commonly runs on a separate machine from everything else, so its address is always trusted exactly as configured. The other services are assumed to sit alongside PLAY itself, and their addresses are worked out accordingly.

What happens if a required setting is missing everywhere?

It's reported clearly at startup, and PLAY is told the value is empty rather than being handed a guess — reported once, at the source, instead of surfacing later as a confusing broken behavior.

Can each organization set its own AI assistant name and other preferences?

Yes — the organization-level settings above are configured independently per organization, so different organizations sharing the same deployment can each have their own values.
