Infrastructure

Response Headers Configuration

CORS behavior and HTTP response headers on the PlayService API are driven entirely by .env values. No code change or redeploy of application logic is needed to change an allowed origin, tighten a security header, or stop leaking a header like X-Powered-By.

playservice4.x·app.js Config file·playservice4.x/.env

01

What this covers

One Express server, one place to configure it.

The PlayService API — the backend serving all /play-api/... routes — reads a small set of APP_* environment variables at startup and uses them to build every response's CORS and security headers, and to decide which headers (if any) should be stripped before the response leaves the process. All of this logic lives in initExpress() in app.js.

Restart required

.env is loaded once, at process startup. Editing a value on a running server has no effect until the process is restarted.

02

CORS settings

Controls which origins may call the API and what the browser is told is allowed.

APP_CORS_ORIGIN default *

Which origins get Access-Control-Allow-Origin echoed back. Set to * to allow any origin, or a comma-separated allow-list of specific origins to restrict it.

e.g. APP_CORS_ORIGIN=https://app.example.com,https://admin.example.com

APP_CORS_METHODS e.g. DELETE, POST, GET...

Value sent as Access-Control-Allow-Methods. List every HTTP verb a client is allowed to send cross-origin.

e.g. APP_CORS_METHODS="DELETE, POST, GET, OPTIONS, PATCH, PUT"

APP_CORS_HEADERS e.g. Content-Type, Authorization...

Value sent as Access-Control-Allow-Headers. List every request header a client is allowed to send cross-origin.

e.g. APP_CORS_HEADERS="Content-Type, Authorization, Origin, Accept, X-Requested-With, x-access-token"

Origin matching is exact

When not using *, the incoming request's Origin header must match one of the comma-separated values exactly (protocol and host, no wildcards, no trailing slash) or no Access-Control-Allow-Origin header is sent at all — the browser will then block the response.

03

Security response headers

Optional headers, added only when a value is set.

APP_CONTENT_TYPE e.g. application/json

Sets a default Content-Type response header. Leave unset to let each route decide its own content type.

APP_X_FRAME_OPTIONS e.g. DENY

Sets X-Frame-Options, controlling whether the site can be embedded in an <iframe>. Use DENY to block framing entirely, or SAMEORIGIN to allow it only from the same origin.

APP_CONTENT_SECURITY_POLICY e.g. frame-ancestors 'none'

Sets the Content-Security-Policy header. See the callout below — PlayService also hard-sets frame protection unconditionally, on top of whatever this variable adds.

Frame protection is double-set

X-Frame-Options: DENY and Content-Security-Policy: frame-ancestors 'none' are also set unconditionally in code, after the env-driven headers. So even if APP_X_FRAME_OPTIONS or APP_CONTENT_SECURITY_POLICY is left blank, framing is still blocked by default on this server.

04

Removing headers

Stop the server from leaking headers that fingerprint the underlying stack.

APP_REMOVE_HEADERS default X-Powered-By

Comma-separated list of response header names to remove from every response. X-Powered-By is handled specially — it's disabled at the Express app level via app.disable('x-powered-by') so it's never set in the first place, rather than being stripped after the fact. Any other header named here is removed per-response with res.removeHeader().

e.g. APP_REMOVE_HEADERS="X-Powered-By, Server"

Matching is case-insensitive, list-driven

Only headers explicitly named in APP_REMOVE_HEADERS are affected. An empty or missing value means no header is stripped — including X-Powered-By, which will then be sent with the default Express value.

05

Example .env block

The current default configuration.

PlayService playservice4.x/.env

.env
# Express server and CORS Configurations
APP_CORS_ORIGIN=*
APP_CORS_METHODS="DELETE, POST, GET, OPTIONS, PATCH, PUT"
APP_CORS_HEADERS="Content-Type, Authorization, Origin, Accept, X-Requested-With, x-access-token"
APP_CONTENT_TYPE="application/json"
APP_CONTENT_SECURITY_POLICY="frame-ancestors 'none'"
APP_X_FRAME_OPTIONS="DENY"
# Comma-separated list of response headers to strip
APP_REMOVE_HEADERS="X-Powered-By"

06

Good to know

A few things that come up when tuning these values.

I changed a value in .env but nothing changed. Why?

The server process must be restarted. These values are read once at startup, not watched or hot-reloaded.

Can I allow more than one origin?

Yes — set APP_CORS_ORIGIN to a comma-separated list of exact origins instead of *. Each request's Origin header is checked against that list.

What happens if I leave APP_REMOVE_HEADERS blank?

No headers are stripped, and X-Powered-By: Express is sent as normal. Set it explicitly (at minimum X-Powered-By) to stop advertising the framework in every response.

Does removing a header ever break a client?

Not for anything in the default list — X-Powered-By is purely informational fingerprinting and no client logic depends on it. Be more careful before adding CORS or content headers to this list, since those can be functionally required by browsers or downstream consumers.

07

Field reference

Every environment variable this configuration reads.

VariableDefaultDescription
APP_CORS_ORIGIN * * for any origin, or a comma-separated allow-list of exact origins.
APP_CORS_METHODS — Value sent as Access-Control-Allow-Methods.
APP_CORS_HEADERS — Value sent as Access-Control-Allow-Headers.
APP_CONTENT_TYPE — Default Content-Type response header, if set.
APP_X_FRAME_OPTIONS — X-Frame-Options value, e.g. DENY or SAMEORIGIN. Framing is blocked regardless — see callout above.
APP_CONTENT_SECURITY_POLICY — Content-Security-Policy value, e.g. frame-ancestors 'none'.
APP_REMOVE_HEADERS X-Powered-By Comma-separated header names to strip from every response. X-Powered-By is disabled at the Express level; anything else is removed per-response.
