Recordings

Record Media Lookup

One endpoint gets you the playable link for a single call or chat recording, or a browsable page of recordings for a whole process and channel — which one you get back depends only on whether you tell it which recording you want.

GET/play-api/record-media/:campaign/:channel 4.16.1.2.2_hotfix·Released 2026-08-20

01

What this endpoint does

A short primer before you send a request.

Every recorded interaction — a call, chat, or email — has a media file sitting somewhere your storage is configured to keep it. This endpoint turns that internal storage location into a link you can actually play or download, so a client app never needs to know how or where a recording is stored.

It supports two distinct requests behind one route:

  • Look up one recording — you already know its Record ID or Session ID, and want its link back.
  • Browse recordings — you want a page of what's available for a process and channel, e.g. to populate a recordings list in a dashboard.

02

Two ways to use it

Sending an ID switches the whole response shape — there's no separate flag to set.

1

Get one recording

You already know which interaction you want.

Send recordId or xsessid → you get back one playback link.
2

Browse recordings

You want to see what's available for a process and channel.

Leave out recordId and xsessid → you get back a page of recordings for that campaign + channel.
Good to know

If you send both an ID and paging params in the same request, the ID wins — the request always resolves to single-recording mode, and limit/offset/includecount are silently ignored.

03

Paging through a list

Three optional settings control what a "browse" request gives you back. None of them do anything in single-lookup mode.

limit default 20

How many recordings to return in one page. Ask for more than 30 and you'll still only get 30 back — that ceiling keeps responses fast. An unreadable or missing value falls back to the default.

e.g. limit=10 → up to 10 recordings per page.

offset default 0

How many recordings to skip before your page starts. Pair it with limit to move through pages: page 1 is offset=0, page 2 is offset=limit, page 3 is offset=limit×2, and so on.

e.g. limit=20&offset=20 → recordings 21–40.

includecount default off

Set to true when you need to show something like "showing 20 of 3,464" or build page numbers. It adds a totalCount field with the full count of matching recordings, not just this page's size.

Leave it off for a simple "load more" flow — the total costs an extra database round-trip on every request.

Invalid values don't error

A missing, empty, or non-numeric limit falls back to 20; anything over 30 is capped at 30. A missing, non-numeric, or negative offset falls back to 0. Only the literal string "true" (case-insensitive) turns includecount on — anything else, including 1 or a missing value, is treated as off.

04

Filtering by date & ordering

Two optional settings narrow a "browse" request to a date range, and a third controls the order results come back in. Like the paging params, none of them does anything in single-lookup mode.

fromdate default none

Earliest date to include, inclusive. Whatever time of day you send is ignored — the filter always starts at the very beginning of that date. Leave it out entirely and there's no lower bound.

e.g. fromdate=2026-08-01 → recordings from Aug 1st onward.

todate default none

Latest date to include, inclusive. Whatever time of day you send is ignored — the filter always ends at the very end of that date. Leave it out entirely and there's no upper bound.

e.g. fromdate=2026-08-01&todate=2026-08-07 → Aug 1st through Aug 7th, inclusive.

orderby default varies

Sort direction for the page you get back: asc or desc (case-insensitive), by recording start time. Sending anything else is rejected. It only changes ordering, never which recordings match — combine it with limit/offset to page through a large result set in either direction.

e.g. orderby=asc → oldest matching recording first.

Neither date is defaulted anymore

Unlike limit/offset, missing fromdate/todate are never filled in with today's date — they're simply left out of the filter. What you get back depends on which side you send:

  • Neither sent — no date filter at all; you get the most recent recordings, newest first, capped at limit.
  • Only fromdate — everything from that date onward, no upper bound; returned oldest-first from fromdate, capped at limit.
  • Only todate — everything up to that date, no lower bound; returned newest-first up to todate, capped at limit.
  • Both sent — a fixed range, validated as below. This is the only combination checked against the server's max-range setting.

Add orderby to any of the four combinations above to force that specific sort direction instead of the default just described.

Rejected, not silently corrected

Unlike limit/offset, a bad date or order value is rejected rather than corrected for you. That includes: a date that isn't YYYY-MM-DD or ISO 8601, either date later than today, an orderby that isn't asc/desc, and — only when both fromdate and todate are sent — fromdate later than todate, or a span wider than the server's configured maximum (90 days by default).

05

Example: getting one recording

Send an ID, get back one link.

Request by xsessid

request
GET /play-api/record-media/CROSSX_PROCESS/call?xsessid=bf8a812dec0e4b458184fcc67dc1bb1e
x-access-token: <your token>

Response 200

response
{
  "status": 200,
  "mediaFileName": "...20251202124058_3508498034245506.wav",
  "mediaFilePath": "http://.../play-api/media/<link>.wav",
  "timeStamp": "2026-08-19 17:09:20"
}

mediaFilePath is the link to play or download that recording. Token and link shortened here for this document — yours will be a full working URL.

06

Example: browsing a page of recordings

Leave out the ID, get back a page.

Request limit, offset, includecount

request
GET /play-api/record-media/CROSSX_PROCESS/call?limit=5&offset=0&includecount=true
x-access-token: <your token>

Response 200

response
{
  "status": 200,
  "records": [
    { "mediaFileName": "...20250926201055.wav", "mediaFilePath": "http://.../<link>.wav" },
    { "mediaFileName": "...20250926202207...wav", "mediaFilePath": "http://.../<link>.wav" },
    // ...3 more (5 total, matching limit=5)
  ],
  "timeStamp": "2026-08-19 17:10:03",
  "totalCount": 3464
}

5 recordings on this page, out of 3,464 total for this process + channel. To see the next 5, repeat the request with offset=5.

07

Good to know

A few things that come up once you start integrating.

Why might a recording be missing from a browsed list?

Only recordings whose storage location resolves to a real, playable link are included — if one can't be resolved, it's quietly left out of the page rather than returned broken.

Does includecount do anything for a single lookup?

No — it's ignored whenever recordId or xsessid is present, since a single-recording response is never paginated or counted.

Can I raise the 30-record page cap?

That ceiling is configurable on the server — if your integration regularly needs bigger pages, ask whoever manages the deployment rather than assuming a client-side limit can exceed it.

Do fromdate/todate/orderby do anything for a single lookup?

No — like limit and offset, they're ignored whenever recordId or xsessid is present.

Can I raise the 90-day max range?

That ceiling is configurable on the server, the same way the page-size cap above is — ask whoever manages the deployment if your integration needs a wider range. It's only enforced when both fromdate and todate are sent; an open-ended query (one side or neither sent) has no range cap, just the usual limit on page size.

What order do I get results in if I don't pass orderby?

It depends on the date params: no dates or todate-only returns newest first; fromdate-only returns oldest first; sending both fromdate and todate returns them in no particular guaranteed order. Pass orderby explicitly if your integration depends on the order.

08

Field reference

Every query parameter this endpoint reads.

ParamApplies toDescription
recordId — Exact record ID. If present, forces single-lookup mode.
xsessid — Exact session ID. If present, forces single-lookup mode.
limit List only Records per page. Default 20, clamped 1–30.
offset List only Records to skip before the page starts. Default 0.
includecount List only Set true to add totalCount to the response.
fromdate List only Earliest date, inclusive (YYYY-MM-DD or ISO 8601). No default — omit for no lower bound. Time of day is ignored. Must not be after today.
todate List only Latest date, inclusive. No default — omit for no upper bound. Must not be after today; when fromdate is also sent, must not be before it or more than the server's configured maximum (90 days by default) after it.
orderby List only asc or desc, sorted by recording start time. Overrides the date-based default sort order.
content_format Single lookup Output format hint for chat/email channels (e.g. json, txt, pdf).
xconnid Single lookup Picks a specific connection leg's media within one record instead of the top-level session media.
